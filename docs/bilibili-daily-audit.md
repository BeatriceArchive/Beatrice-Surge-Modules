## 1.11.2 实机失败反馈与恢复修复

2026-10-05 05:32，用户截图确认已加载 1.11.1，分享仍显示 `code -403`，文案为“每日分享任务未确认；今日写入次数已用尽”。该文案来自复用当天 `share_attempt` 后的确认分支，证明截图这轮没有新的分享 POST；截图无法判断原始拒绝来自哪个版本，也没有原始响应 message。因此不能将“模拟测试通过”表述为此账号的分享故障已解决。

确认的缺陷是：明确拒绝与不确定结果都占用整天一次的本地额度；通知不区分历史失败与本轮请求；原始 HTTP 状态和 message 在保存时丢失。“次数已用尽”来自脚本的本地策略，并非 B 站返回的每日额度。

本次改动：

- 保留当前曾实机成功的 PC-client 表单、Cookie 会话与出站策略。没有证据支持通过换参数、UA、出口或构造设备指纹来修复本账号的 -403，不作这些改动。
- 仅 HTTP 2xx 内明确 API `-403` 且 `requestSucceeded=false / confirmed=false` 的记录，允许后续一次 **Panel 按钮** 补试。新记录至少间隔 60 秒；全天最多两次请求，cron 不自动补试。60 秒是本地节制策略，不是 B 站公布的限流窗口。
- 旧版明确 -403 拒绝记录没有时间戳，手动刷新可补试一次并迁移到 v3 记录；旧版缺少明确失败标记、损坏、已成功或不确定记录均不释放。自动刷新不执行请求。
- v3 在发送前持久化次数和时间，结果保存失败保留不确定占额；网络超时、HTTP 403/5xx、API 0/71000、显式风控及未知结果均不获得第二次写入。
- 拒绝通知明确显示“本轮已提交”或“历史失败，本轮未提交”，记录北京时间、HTTP 状态和经过 Cookie/CSRF 值、链接及长 token 脱敏的 message。不保存完整请求/响应、Cookie 或 Authorization；诊断仅保存在 Surge 本地。
- 投币预算不改动；截图硬币余额为 0，投币 1/5 不能靠重试补满。

新增 12 项回归，全仓库 420 项测试。本轮修复的是可复现的恢复和诊断缺陷，**服务端 -403 的根因仍未证实，不能宣称分享实机已恢复**。更新后手动刷新一次，凭新通知判断新请求及其响应；若仍拒绝，需以新响应继续定位，不循环提交。

## 1.11.1 分享功能专项

首轮 1.11.0 主要修复公共执行保护，未修复分享功能的内部阻断；用户要求专项补齐后，1.11.1 改动以下实际执行逻辑：

1. **候选视频独立于播放资料。** 旧 `share()` 复用 `video()`，必须同时拿到 aid 和 CID 才肯分享；CID 对分享没有用途。现优先复用动态 / 排行榜中的 aid，缺少 CID 不再阻断；资料查询临时不可用时使用已有的合法 BVID，已删除稿件则换下一个候选。每天仍只发送一次分享 POST，不轮换参数刷接口。
2. **解除不必要的排行榜前置依赖。** 有可用动态稿件时立即用于观看 / 分享；投币候选不足需要补排行榜，放在分享完成之后。排行榜异常不再阻止原本可执行的分享。
3. **延长异步到账确认。** 旧版只有累计 3.7 秒等待，新增的 12 秒延迟到账场景可复现提前报失败。现采用 0 / 1.2 / 2.5 / 5 / 10 秒分段等待（累计 18.7 秒，另计 HTTP 时间）；始终受整轮预算约束。API 0 / 71000 仅表示进入待确认，只有官方 `share=true` 才完成。
4. **保留已确认的当日成果。** 旧版分享确认接口已返回 true，但最后一次日状态返回 false 时会抹掉结果。现合并本轮和当日已持久化的官方成功证据；跨日不沿用。首次结果不确定则显示“分享待确认”，再次刷新只查状态。

对比读取 BLTH 的 `shareTask.ts` 和 `bili-api/index.ts`，以及 BiliBiliToolPro 的 `ShareVideoRequest.cs`。目前仍没有证据证明换 UA、添加更多指纹或改回 web_normal 能解决此账号的 403，因此不猜测修改。aid / bvid 二选一的接口约定也与现有 [API 收集文档](https://github.com/BACNext/bilibili-API-collect-backup/blob/master/docs/video/action.md) 一致。

这些是已用生产函数复现并修复的分享流程问题，**不是对用户当前 -403 根因的实机证明**。服务端明确拒绝仍如实报告；本轮没有用户手机上的最新错误响应，也没有使用真实 Cookie 调用分享接口。

- 超时、进程被终止、结果保存失败或记录损坏：当天不再投币，次日恢复。其余可独立执行的任务继续按各自结果判断。不要通过删除记录来强行补投。
- 未使用真实账号做写操作；模拟投币记录没有写入手机。升级不要求清除 Cookie 或既有分享去重记录。
- 每次运行最多补到 5 枚的普通任务目标；其他客户端同时投币仍存在服务端查询与写入之间的竞争，脚本无法提供跨客户端事务保证。
- 08:00 cron 随设备时区；B 站任务日期与本地去重按 UTC+8。自动 Panel 刷新不会执行网络请求或补签到。

## 依据

- [Surge JavaScript API](https://manual.nssurge.com/scripting/api.html)：触发来源、请求状态、超时秒数、禁用自动 Cookie / 跳转、持久化写入返回值。
- [Surge cron](https://manual.nssurge.com/scripting/cron.html) 与 [脚本运行时限](https://manual.nssurge.com/scripting/overview.html)：正常 cron 不带 Panel 输入；脚本须在 timeout 前完成。
- [BLTH 当前接口实现](https://github.com/andywang425/BLTH/blob/3fd9d80086f303985ec4d2dad7c9947861da2805/src/library/bili-api/index.ts)：本次读取的上游 HEAD。确认分享仍采用 `pc_client_normal`，大会员经验请求使用 mid / buvid / csrf。第三方源码只作为请求形态依据，不代表 B 站官方承诺，也不证明此账号一定通过风控。
- 既有分享实机依据见 [会话与分享说明](bilibili-session-share.md)。未因上游新增参数而整体替换已验证的观看、分享和投币请求。

## 验证边界

新增隔离回归覆盖网络 / 认证分类、身份不一致、GET 重试、跨运行投币上限、未知结果、持久化失败、日期切换、账户切换、运行锁、余额不足、经验延迟、最终确认、真实 cron 入口形态与完整任务成功路径。测试仅使用假 Cookie 和本地模拟响应。

首轮新增 45 项测试，分享专项再新增 11 项；全仓库共 408 项。脚本语法、模块元数据 / 引用以及固定 Config 版本的 18 项 General 契约一并检查。首轮时区相关场景另在 Asia/Shanghai 环境检查，日期夹具与北京时间去重正常。

全仓库测试另发现一个基础面板测试将固定 Unix 时间戳硬编码为北京时间日期，导致 UTC 环境失败；仅将该测试的到期时间夹具改为本地同一日的中午，未修改基础面板脚本。

本地语法、模块一致性、Config 契约及行为测试不能代替 iPhone + Surge 的真实任务验收。B 站接口无此用途的稳定公开服务承诺，风控、异步记账、手机后台调度与网络状况仍需看实际运行结果。更新后 Panel 显示 `v1.11.2` 才表示已加载新版脚本。
